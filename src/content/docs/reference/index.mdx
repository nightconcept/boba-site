## API Conventions

### Function Signatures
All standard library functions follow consistent patterns:
- **Error handling**: Functions that can fail return `Result<T, E>`
- **Optional values**: Missing data represented with `Option<T>`
- **Named parameters**: Multi-parameter functions require named arguments
- **Immutability**: Functions return new values rather than modifying inputs

### Type Notation
- `T[]` - Array of type T
- `[K:V]` - Map with keys of type K and values of type V
- `Option<T>` - Optional value of type T
- `Result<T, E>` - Result that's either Ok(T) or Err(E)
- `T...` - Variadic parameters of type T

### Error Types
Standard error types used throughout the library:
- `IoError` - File system and network I/O errors
- `ParseError` - Data parsing and conversion errors
- `ValueError` - Invalid input or range errors
- `SystemError` - Operating system and runtime errors

## Usage Patterns

### Import Conventions
```boba
import std:fs                    // Import entire module
import std:json.{parse, stringify}  // Import specific functions
import std:http as client           // Import with alias
```

### Error Handling Patterns
```boba
// Explicit error handling
let result = fs.read("file.txt")
match result {
    Ok(content) => process(content),
    Err(error) => handle_error(error)
}

// Error propagation
fn read_config(): Result<Config, string> {
    let content = fs.read("config.json")?
    let config = json.parse(content)?
    Ok(config)
}
```

### Working with Options
```boba
// Safe access to optional values
let user_email = user.email.unwrap_or("no-email@example.com")

// Chaining operations
let formatted = user.email
    .map(|email| email.to_lower())
    .unwrap_or("unknown")
```
